# Авторизация: список изменений и описание

Дата: 11 октября 2026 года.

Продолжена подготовленная ранее реализация. Существующие модели пользователя/сессии,
схемы валидации, Argon2-хеширование, сервис создания пользователя и первые две миграции
сохранены и использованы. Рабочий администратор не пересоздавался.

## 1. Первый администратор

`app/cli/create_admin.py`, `app/services/users.py`.

Проверка наличия администратора перенесена в сервис; CLI отвечает за аргументы и вывод.
Проверка/создание сериализованы SQLite-транзакцией, чтобы одновременные команды не
создали двух первых администраторов. После первого новые аккаунты создаются через
защищённый API или интерфейс. Публичной регистрации нет.

## 2. Схемы авторизации

`app/schemas/auth.py`.

Добавлены запросы подтверждения, установки пароля по специальному JWT и refresh,
ответы трёх состояний: обычный вход, подтверждение, установка пароля. Нативный клиент
получает JWT в JSON, браузер — статус без значений JWT. Новый пароль проверяется по
согласованным правилам: 15–128 печатных символов, без проверки распространённости.
Для проверки уже существующего пароля достаточно длины 1–128: короткий неверный пароль
даёт обычную ошибку входа; правила нового пароля применяются только при установке.

## 3. JWT и настройки

`app/core/tokens.py`, `app/core/config.py`, `.env.example`.

Добавлены подписание HS256, проверка подписи/алгоритма/срока/издателя/аудитории и
обязательных полей. Назначения JWT: `access`, `refresh`, `login_confirm`, `password_setup`;
маршруты принимают только подходящий тип. Access ограничен 15 минутами и окончанием
сессии. Refresh действует до абсолютного конца 12-часовой сессии. Подтверждение/setup —
5 минут. В JWT нет пароля, хеша, ФИО или роли: актуальное состояние берётся из БД.
Настройки дополнены URL базы, issuer/audience и Secure cookies. `.env` не изменён.

## 4. Вход и одна сессия

`app/services/auth.py`.

Argon2-проверка выполняется в отдельном потоке. Неизвестный логин и неверный пароль
получают одинаковую ошибку. На пользователя допускается одна незавершённая сессия.
Истёкшая закрывается перед новой, освобождая уникальный индекс. При существующей
активной сессии выдаётся только подтверждение, прежняя сессия пока работает.
Подтверждение связано с конкретной старой сессией и версией пароля: повтор старого
запроса не завершает новую сессию. Запись сериализуется `BEGIN IMMEDIATE`, что
предотвращает нарушение ограничения при одновременных входах.

## 5. Установка, смена и сброс пароля

`app/services/auth.py`, `app/models/user.py`,
`migrations/versions/c83170d591a2_add_credential_version.py`.

Временный пароль даёт только setup-JWT без доступа к складу. Он не расходуется при
неудачной установке и не имеет срока годности. Успешная установка создаёт обычную
сессию и делает временный пароль недействительным. Общий `_replace_password`
используется при первой установке, своей смене и административном сбросе: меняет хеш,
признак установки, версию пароля и завершает сессию пользователя. `credential_version`
делает старые токены, включая pending login/setup, недействительными после смены.
Своя смена требует текущего пароля и нового входа. Сброс администратором генерирует
новый временный пароль для аккаунта любой из двух ролей.

## 6. Refresh и выход

`app/services/auth.py`, `app/routers/auth.py`.

Refresh проверяется по UUID `jti` из сессии. После обновления сохраняется новый UUID
и возвращается новая пара JWT; сам refresh в базе не хранится. `expires_at` не сдвигается.
Повтор старого refresh завершает сессию; завершение фиксируется до возврата ошибки,
не откатывается вместе с ней. Logout закрывает сессию, у браузера также очищает cookies.
Состояние сессии проверяется при каждом защищённом запросе: старые токены теряют
доступ сразу, не только после истечения `exp`.

## 7. Роутеры и права

`app/dependencies.py`, `app/core/errors.py`, `app/routers/auth.py`, `app/routers/users.py`,
`app/routers/api_router.py`, `app/routers/products.py`, `app/routers/shelves.py`,
`app/routers/shelf_stock.py`.

Общая зависимость принимает Bearer access или access-cookie и возвращает проверенный
контекст пользователя/сессии. Все складские методы требуют входа. Удаление товара
и снятие с полки защищены ролью администратора в JSON API **и** в прежних POST-формах.
Добавлены административные список/создание пользователей и сброс пароля.
Подключён существующий health-роутер, ранее не включённый в `api_router`.
Отсутствующая связь товара с полкой при удалении теперь даёт 404 вместо внутренней
ошибки при попытке удалить `None`.

## 8. Интерфейс и cookies

`app/core/cookies.py`, `app/static/auth.js`, `app/static/login.html`,
`app/static/password.html`, `app/static/users.html`, `app/static/index_style.css`,
шесть существующих складских HTML-страниц.

Страница входа переключается между логином/паролем, установкой постоянного пароля
и модальным подтверждением «Вы уже вошли». Отмена не меняет прежнюю сессию.
Добавлены смена пароля и управление пользователями обеих ролей с выдачей временного
пароля. Пароль виден только в результате создания/сброса, не сохраняется в браузерном
хранилище. Складские формы используют общий клиент запросов; добавлена панель ФИО,
роли, смены пароля и выхода. Ссылки удаления скрыты у работника.

JWT находятся в HttpOnly cookies; JavaScript читает только CSRF-cookie. Изменяющие
cookie-запросы требуют подписанный CSRF в заголовке, связанный с входом/сессией.
Контекст проверяется и на складских маршрутах, куда refresh с узким путём не отправляется.
Access обновляется автоматически после 401. Одновременные запросы используют одно
обновление; Web Locks согласует refresh между вкладками. Ошибки доступа/бизнес-логики
не вызывают бесконечных повторов. Формы паролей используют POST даже без JavaScript,
поэтому секреты не попадают в URL при ошибке загрузки клиентского кода.

## 9. Подключение БД и HTTP

`app/db.py`, `app/main.py`.

URL базы берётся из настроек. В SQLite включены внешние ключи и ожидание блокировки
до 10 секунд. При остановке освобождается пул соединений; таблицы создаются миграциями.
Ошибки авторизации имеют HTTP-статус, описание и код; 401 — `WWW-Authenticate: Bearer`.
Ответы API не кэшируются; ошибки валидации не возвращают значения паролей/JWT и тела
запросов. Добавлен `X-Content-Type-Options: nosniff`.

Из кода подключения к БД удалён комментарий с открытым временным паролем.
Пароль существующего аккаунта не менялся. Если комментарий ранее публиковался,
удаление не очищает историю Git: смените пароль и отдельно проверьте публикации.

## 10. Тесты и документация

`tests/conftest.py`, `tests/test_auth.py`, `tests/test_migrations.py`,
`tests/auth_client.test.cjs`, `requirements-dev.txt`, `README.md`, этот документ.

В `requirements.txt` для uvloop добавлен маркер исключения Windows: библиотека
не поддерживает эту платформу и не нужна стандартному asyncio-циклу приложения.
Версии остальных ранее указанных зависимостей не менялись.

Проверены вход/неверные реквизиты; первый пароль и неудачная установка;
подтверждение/отмена/истечение/replay; сроки access и сессии; rotation/reuse refresh;
смена/сброс и старые JWT; создание обеих ролей/уникальность/отказ второго bootstrap;
права обеих ролей, включая JSON и HTML удаления; cookies/CSRF/подделка/выход;
неправильные JWT claims; одновременные входы, refresh и setup;
миграции пустой/существующей базы; подключение auth-скрипта ко всем страницам;
клиентские повторы и межвкладочная блокировка refresh.

Результат: **60 Python-тестов и 8 JavaScript-тестов прошли**. Проверка синтаксиса JS
прошла. `alembic check` не нашёл расхождений моделей и схемы. Страница входа открыта
и визуально проверена в браузере, ошибок JavaScript не найдено. Полный UI-проход с
рабочим аккаунтом не выполнялся: администратор не использовался для тестов.
Сценарии API проверены на отдельных базах. Python выдал два предупреждения
deprecated-интерфейсов установленного Starlette/httpx/anyio, без ошибок тестов.

## Границы реализации

- Backend готов для будущего Expo-клиента; само приложение Expo не создавалось.
- Блокировка, массовый выход и публичная регистрация не добавлены.
- Сохраняется SQLite. Блокировки требуют пересмотра при переходе на PostgreSQL.
- HTTPS, Secure cookies и ограничение частоты запросов нужны перед публикацией;
  ограничение частоты не встроено в приложение.
- Без Web Locks используйте одну вкладку, иначе параллельное обновление может
  запустить предусмотренную защиту от повторного refresh.
- Рабочая база уже отслеживается Git. Не публикуйте её, `.env` и резервные копии.

При проверке реализации использована официальная документация
[PyJWT](https://pyjwt.readthedocs.io/en/latest/api.html) и
[Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API).
