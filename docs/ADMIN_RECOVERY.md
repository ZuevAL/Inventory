# Восстановление доступа администратора

## Обновление

Из корня проекта выполните `alembic upgrade head` через Python виртуального
окружения, затем перезапустите приложение. Миграция `d94281e6ac03` добавляет поля
резервных кодов и таблицы `recovery_events`, `recovery_limits`. Существующие аккаунты,
пароли, сессии и складские данные сохраняются. Рабочая база не изменяется тестами.

Все существующие и новые администраторы без активного резервного кода проходят
настройку через `/static/security.html`. Ограничение складских операций проверяется
сервером для Bearer и cookie-запросов. Вход, выход, обновление сессии, смена своего
пароля, настройка восстановления и просмотр своей истории остаются доступны.
Работникам резервный код не выдаётся.

## Выпуск и сохранение

1. Администратор открывает «Безопасность» и вводит текущий пароль.
2. Приложение один раз показывает новый код: 128 случайных бит, 32 шестнадцатеричных
   символа в группах. Его можно скопировать или скачать текстовым файлом.
3. Администратор сохраняет код вне браузера и подтверждает сохранение.
4. Код активируется. До подтверждения замены предыдущий активный код сохраняется.

Подтверждение возможно в течение 15 минут и только в той же действующей сессии,
в которой выпущен код. Новая выдача заменяет предыдущую неподтверждённую выдачу.
Перезагрузка или закрытие страницы не позволяют повторно получить показанный код:
нужно снова выпустить новый. При незавершённой первоначальной настройке приложение
снова направит администратора в «Безопасность».

После активации код действует без ограничения времени. В базе сохраняются только
SHA-256 хеши высокоэнтропийных кодов; открытый код не хранится и не возвращается
при чтении аккаунта, списка пользователей или истории.

## Восстановление

На `/static/recovery.html` вводятся логин, код, новый пароль и повтор нового пароля.
Пробелы и дефисы между группами кода, а также регистр букв несущественны. Пробелы
в пароле, напротив, сохраняются. Пароль — от 15 до 128 печатных символов,
отличается от прежнего.

До успешного сохранения пароль и действующие сессии не меняются. Ошибки заполнения
и неверные попытки не расходуют код. В одной транзакции успешного восстановления:

- устанавливается постоянный пароль и повышается версия учётных данных;
- завершаются прежние сессии и становятся недействительными старые auth-токены;
- аннулируются активный и неподтверждённый резервные коды;
- записывается событие восстановления.

Повторное или одновременное применение одного кода не может установить второй
пароль. Восстановление не создаёт сессию: пользователь возвращается ко входу,
затем сохраняет новый код перед продолжением работы.

Обычная смена пароля с вводом текущего сохраняет активный код. Сброс другим
администратором или CLI аннулирует его и требует настройки заново.

Если код не был настроен заранее либо потеряны и код, и пароль, используется
существующая команда:

```powershell
.\.venv\Scripts\python.exe -m app.cli.reset_admin_password --login admin_01
```

Универсального кода восстановления нет. Почта, SMS и внешние сервисы не требуются.

## Защита и история

- Для неверного логина, неподходящей роли и неверного кода — один ответ.
- Восстановление: до 5 попыток для пары логин/источник и до 30 попыток с одного
  источника за фиксированные 15 минут. Ограничения хранятся в SQLite и разделяются
  процессами; отклонённые запросы не продлевают окно. Ответ 429 содержит `Retry-After`.
  Повторные отклонения объединяются в одно событие для аккаунта/источника в пределах
  окна, чтобы поток заблокированных запросов не раздувал журнал.
- Выпуск кода также ограничен 5 попытками за 15 минут в текущей сессии, включая
  проверки текущего пароля. Ограничения не блокируют обычный вход.
- Cookie-запросы требуют CSRF. Для размещения вне локального компьютера нужны
  HTTPS и Secure cookies, как и для остальной авторизации.
- Источник берётся из ASGI `request.client`, без самостоятельного чтения
  `X-Forwarded-For`. За прокси настройте доверенные адреса прокси в ASGI-сервере;
  не доверяйте заголовкам произвольных клиентов.
- История содержит только время, результат и источник. Секреты и тела запросов
  не записываются. Администратор видит только свой аккаунт. События старше 90 дней
  удаляются при следующей попытке восстановления или чтении истории; старые окна
  ограничителя очищаются при следующем обращении к нему.

## Маршруты

Префикс — `/api/v1`. Изменяющие запросы с cookie требуют `X-CSRF-Token`.

| Маршрут | Доступ и тело |
| --- | --- |
| `GET /auth/me` | Своя сессия; поле `recovery_required` сообщает о необходимости настройки |
| `POST /auth/recovery/code` | Своя сессия администратора; `current_password`; возвращает `recovery_code`, `expires_in` |
| `POST /auth/recovery/activate` | Та же сессия; `recovery_code`, `saved: true` |
| `GET /auth/recovery/history?offset=0&limit=100` | Своя сессия администратора; история с пагинацией |
| `POST /auth/web/password/recover` | Без сессии, с CSRF; `login`, `recovery_code`, `new_password`, `repeat_password` |

Все ответы API имеют `Cache-Control: no-store`. Включение журналирования тел
запросов или ответов на прокси недопустимо: они могут содержать секреты.
