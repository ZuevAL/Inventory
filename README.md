# Inventory API

Складское приложение: FastAPI, SQLAlchemy, SQLite. Авторизация — PyJWT (HS256),
пароли — pwdlib/Argon2, схема базы — Alembic.

## Запуск в Windows

Команды выполняются из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Если `.env` уже настроен, не заменяйте существующий JWT-ключ. Для новой установки
создайте `.env` по образцу `.env.example`. Получить случайный ключ:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))"
```

Сохраните результат только в `JWT_SECRET_KEY` своего `.env`. Смена ключа делает
выданные токены недействительными. Настройки:

- `ACCESS_TOKEN_EXPIRE_MINUTES=15` — access JWT;
- `SESSION_EXPIRE_HOURS=12` — абсолютное время сессии;
- `LOGIN_CONFIRM_EXPIRE_MINUTES=5` — подтверждение повторного входа;
- `PASSWORD_SETUP_EXPIRE_MINUTES=5` — запрос установки постоянного пароля;
- `AUTH_COOKIE_SECURE=False` — только для локального HTTP;
- `DATABASE_URL=sqlite+aiosqlite:///./sql_app.db` — текущая SQLite-база.

Таблицы создаются миграциями, а не при запуске приложения.
Веб-интерфейс: [страница входа](http://127.0.0.1:8000/static/login.html).
Открывайте HTML через сервер, не двойным щелчком по файлу. `/` остаётся JSON.

## Первый администратор

Только на базе без администратора:

```powershell
.\.venv\Scripts\python.exe -m app.cli.create_admin --login admin_01 --full-name "Иван Петров"
```

Команда выводит временный пароль. Сохраните его безопасным способом. При наличии
администратора команда отказывает. Другие аккаунты обеих ролей создаются через
раздел «Пользователи». Публичной регистрации нет.

При первом входе пользователь устанавливает постоянный пароль. Временный пароль
не имеет срока годности и работает до успешной установки постоянного. Истечение
5-минутного setup-токена не уничтожает временный пароль: можно повторить вход.

## Роли, пароли и сессии

- Администратор выполняет все складские действия, создаёт работников/администраторов
  и сбрасывает им пароли.
- Работник выполняет складские действия, кроме удаления товара и снятия товара
  с полки. Управление пользователями — только для администратора.
- На пользователя допускается одна сессия. Вход на другом устройстве требует
  подтверждения завершения предыдущей; отмена её не завершает.
- Access действует не более 15 минут. Refresh выдаёт новую пару JWT, но **не продлевает**
  12-часовую сессию. После её истечения нужен вход с паролем.
- Старый refresh одноразовый: повторное использование завершает связанную с ним
  активную сессию. Не запускайте параллельные refresh и не повторяйте их вслепую
  после сетевого сбоя. Если ответ потерян после обработки, потребуется новый вход.
- Выход, смена/сброс пароля и подтверждённый новый вход немедленно запрещают
  следующие запросы со старыми токенами соответствующей сессии.
- Своя смена пароля требует текущего пароля и завершает сессию. Сброс администратором
  генерирует временный пароль и повторяет процедуру первоначальной установки.
  При сбросе своего аккаунта сохраните выданный пароль до ухода со страницы.

Логин: 3–32 латинских буквы, цифры, `.`, `_`, `-`, без пробелов, нижний регистр.
ФИО обязательно. Новый пароль: 15–128 печатных символов, пробелы учитываются.
Требований к составу и проверки распространённых паролей нет. Новый пароль
должен отличаться от заменяемого.

## JSON API для Expo

Префикс: `/api/v1`. Защищённые запросы: `Authorization: Bearer <access_token>`.

| Метод и маршрут | Назначение / JSON |
| --- | --- |
| `POST /auth/login` | `login`, `password` |
| `POST /auth/confirm-login` | `confirmation_token`, `confirm: true` |
| `POST /auth/password/setup` | `password_setup_token`, `new_password` |
| `POST /auth/refresh` | `refresh_token`; новая пара JWT |
| `POST /auth/password/change` | Bearer + `current_password`, `new_password`; завершает сессию |
| `POST /auth/logout` | Bearer access; ответ 204 |
| `GET /auth/me` | Bearer; текущий пользователь |
| `GET /users/?offset=0&limit=100` | Список пользователей, администратор |
| `POST /users/` | `login`, `full_name`, `role`; администратор |
| `POST /users/{id}/reset-password` | Новый временный пароль; администратор |

Ответ входа определяется полем `status`:

1. `authenticated`: `access_token`, `refresh_token`, `token_type: "bearer"`,
   `expires_in` (секунды), `session_expires_at` (Unix-время), `user`.
2. `confirm_login`: `confirmation_token`, `expires_in`, `message`. Показать окно;
   подтверждать только после согласия. При отмене отбросить токен, старую сессию не трогать.
3. `password_setup`: `password_setup_token`, `expires_in`, `message`. Показать форму
   нового пароля. Этот JWT не даёт доступа к складу.

Успешные подтверждение/установка возвращают `authenticated` с парой JWT.
Типы JWT невзаимозаменяемы. Ошибки авторизации:
`{"detail": "Описание", "code": "session_ended"}`. Ошибки валидации — 422 с массивом
`detail`, без возврата введённых паролей/JWT.

В будущем Expo-клиенте: access в памяти, refresh в `expo-secure-store`, промежуточные
JWT — только на время шага. После refresh заменяйте сохранённый refresh; объединяйте
одновременные попытки обновления в один запрос. Если access истёк перед выходом,
сначала обновите его, затем вызовите logout. Мобильное приложение здесь не создавалось.

## Браузер

Тот же JWT-механизм, но токены находятся в HttpOnly cookies, не в JavaScript,
localStorage или sessionStorage. Браузерные маршруты:

- `GET /auth/web/csrf` — устанавливает CSRF-cookie;
- `POST /auth/web/login` — JSON `login`, `password`;
- `POST /auth/web/confirm-login` — JSON `confirm: true`;
- `POST /auth/web/password/setup` — JSON `new_password`;
- `POST /auth/web/refresh`, `/auth/web/logout`, `/auth/web/cancel-login` — без тела;
- `/auth/me` и `/auth/password/change` — общие с JSON API.

Изменяющие cookie-запросы требуют заголовок `X-CSRF-Token`, равный `inventory_csrf`
cookie. Токен подписан сервером и связан с входом/сессией. JWT cookies: `HttpOnly`,
`SameSite=Strict`, в production также `Secure`. Refresh/pending ограничены путём
`/api/v1/auth`. Встроенный клиент сам добавляет CSRF, обновляет access после 401,
отправляет формы и показывает ошибки. Web Locks синхронизирует refresh между вкладками.
Без Web Locks объединение работает только внутри вкладки: используйте одну вкладку.
Для размещения в сети нужен HTTPS. При изменении `API_V1_PREFIX` согласованно
измените префикс и адреса форм в статическом интерфейсе.

используют рабочие аккаунты. `requirements-dev.txt` содержит зависимости и pytest.

## Перед размещением в интернете

Настройте HTTPS, `AUTH_COOKIE_SECURE=True`, случайный приватный JWT-ключ и ограничение
частоты входа/setup/refresh на обратном прокси. Ограничение частоты здесь не реализовано.
Не включайте debug, не логируйте пароли/токены/тела auth-запросов. При необходимости
защитите Swagger. Не разрешайте CORS произвольным сайтам с credentials: встроенный
интерфейс работает с того же origin, нативный Expo-клиент не требует браузерного CORS.

Запись авторизации использует SQLite `BEGIN IMMEDIATE`. Для PostgreSQL/высокой нагрузки
нужно пересмотреть транзакции и блокировки. Завершённые сессии сохраняются;
периодической очистки пока нет. Блокировка аккаунтов и отдельный «выход на всех
устройствах» не добавлены, как и согласовано.

**Не публикуйте `.env`, `sql_app.db` и резервные копии.** База уже отслеживается Git
и содержит хеши паролей. Не включайте её в публичный коммит. Удаление её из истории
Git при необходимости — отдельная операция.
